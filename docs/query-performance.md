# 查询复用验证

## 2026-11-26 按缓存分布复测扫描

使用 `node scripts/compare-scan-profiles.cjs <基线Host.dll> <候选Host.dll> [参考Host.dll]` 可以重建下列三种合成库。脚本为每个版本启动独立的 Release Host，在相同目录上各预热一次，然后轮换执行顺序，记录六轮完整扫描的中位数。默认排除未完成缓存。每轮都核对纳入条数、跳过条数和无法绑定的逻辑分 P 数，计时结束后再校验全部分页摘要。

本机 Windows x64、.NET 11、i7-14650HX 的耗时如下，单位为毫秒：

| 合成库 | PR #48 前 `0cca828` | PR #48 `7429ab7` | 修复后 |
| --- | ---: | ---: | ---: |
| 350 个视频、700 个分 P，其中 694 个未完成 | 114 | 179 | 112 |
| 350 个视频，每个 P1 对应 4 个物理候选 | 237 | 383 | 208 |
| 350 个视频、700 个完整且可唯一绑定的分 P | 333 | 284 | 170 |

三种版本在每种数据分布上均产生相同的全页摘要指纹。多候选库保留 1,400 个物理条目，350 个有歧义的逻辑分 P 均禁止移动。未完成库仅纳入 6 个完成的分 P。Windows 扫描同一 AV 时复用父目录句柄，期间其他进程需等该 AV 扫描结束才能重命名该目录。本轮不包括操作系统冷启动、媒体解码或用户界面绘制。六轮原始样本和各版本的程序集 SHA-256 位于 `artifacts/e2e/scan-profiles-XZAAkh/results.json`。

另在同一份已预热的 10,000 视频、20,000 分 P 合成库上，两版各顺序扫描三次。修复版和 PR #48 的完整请求中位数分别为 4.98 秒和 8.57 秒，纳入数量、身份告警和全部分页摘要均相同。两组记录分别位于 `artifacts/scan-measurement-zTEDMA/results.json` 和 `artifacts/scan-measurement-bCbAhm/results.json`。

扫描测量报告将脚本工作树的提交号与所选二进制分开记录。无论使用本地还是外部 Host DLL，报告都会对实际传入的 Host 及同目录的 Core、Playback DLL 计算 SHA-256，便于核对被测构建。

## 2026-11-11 增量扫描复测

2026-11-11 更新了本地变更测量脚本。每个扫描样本通过请求 ID 核对诊断 ZIP 的 `ScanTiming`，记录实际增量模式和纳入索引的条目数，并比较增量与全扫的全部分页结果。脚本读取 ZIP 时在 Windows 使用 `tar.exe`，在 Linux 使用 `unzip`。

本机 120 视频、240 分 P 的合成库运行三轮移动和恢复。每次移动后的增量扫描读入 1 个条目，恢复后读入 2 个；加入缺少 metadata 的分段后，下一次本地移动触发全量回退并读入 239 个条目。运行方式为 `node scripts/measure-mutation-refresh.cjs 120`。

## 2026-11-04 本地变更后的增量刷新

`node scripts/measure-mutation-refresh.cjs 500` 在新建的 500 视频/1000 分 P 合成元数据库中，顺序执行三轮移动一个分 P、增量刷新、完整扫描、恢复、增量刷新、完整扫描。每轮核对首屏摘要和全库分 P 总数一致；独立契约回归另核对整视频/最后一个 P、全部统计、异常基线回退、取消和物理目录替换。

本机 Windows/.NET 10.0.403 的六个增量样本为 9.06、5.31、3.90、4.24、44.44、6.65 ms；对应完整扫描为 1078.14、1132.38、931.73、1770.38、1351.65、1028.63 ms。初次完整扫描为 8016.12 ms。原始记录与诊断包位于 `artifacts/e2e/mutation-refresh-OhHZKt/`。这是同一进程中的合成库观察，受 JIT、文件系统缓存和机器负载影响，不代表真实媒体吞吐或跨机器 SLA，也不是冷启动扫描前后的对照。

优化只针对已知本地变更：原索引必须没有损坏/被过滤的未完成/无法访问条目且完整覆盖目录；否则完整扫描。沿用未变化分 P 的原始物理身份，不把路径相同的新目录当成原对象；修改后重新发布令牌。手动刷新仍扫描全库，索引持久化留待后续。
