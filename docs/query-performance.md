# 查询复用验证

2026-11-11 更新了本地变更测量脚本。每个扫描样本通过请求 ID 核对诊断 ZIP 的 `ScanTiming`，记录实际增量模式和纳入索引的条目数，并比较增量与全扫的全部分页结果。脚本读取 ZIP 时在 Windows 使用 `tar.exe`，在 Linux 使用 `unzip`。

本机 120 视频、240 分 P 的合成库运行三轮移动和恢复。每次移动后的增量扫描读入 1 个条目，恢复后读入 2 个；加入缺少 metadata 的分段后，下一次本地移动触发全量回退并读入 239 个条目。运行方式为 `node scripts/measure-mutation-refresh.cjs 120`。

## 2026-11-04 本地变更后的增量刷新

`node scripts/measure-mutation-refresh.cjs 500` 在新建的 500 视频/1000 分 P 合成元数据库中，顺序执行三轮移动一个分 P、增量刷新、完整扫描、恢复、增量刷新、完整扫描。每轮核对首屏摘要和全库分 P 总数一致；独立契约回归另核对整视频/最后一个 P、全部统计、异常基线回退、取消和物理目录替换。

本机 Windows/.NET 10.0.403 的六个增量样本为 9.06、5.31、3.90、4.24、44.44、6.65 ms；对应完整扫描为 1078.14、1132.38、931.73、1770.38、1351.65、1028.63 ms。初次完整扫描为 8016.12 ms。原始记录与诊断包位于 `artifacts/e2e/mutation-refresh-OhHZKt/`。这是同一进程中的合成库观察，受 JIT、文件系统缓存和机器负载影响，不代表真实媒体吞吐或跨机器 SLA，也不是冷启动扫描前后的对照。

优化只针对已知本地变更：原索引必须没有损坏/被过滤的未完成/无法访问条目且完整覆盖目录；否则完整扫描。沿用未变化分 P 的原始物理身份，不把路径相同的新目录当成原对象；修改后重新发布令牌。手动刷新仍扫描全库，索引持久化留待后续。
